# Кнопка аудита кода «Забота Рядом»

## Как запустить

1. Откройте корень проекта `web-service` в Finder.
2. Дважды нажмите файл `audit-zabota-code.command`.
3. Дождитесь строки «Аудит кода завершён».
4. Откройте Markdown-отчёт по пути, который будет показан в терминале.

Если macOS не разрешает запуск, откройте Terminal, перейдите в папку проекта и один раз выдайте файлу права:

```bash
chmod +x audit-zabota-code.command
```

После этого файл можно снова запускать двойным кликом. Если Gatekeeper всё ещё блокирует локальный файл, нажмите его правой кнопкой мыши, выберите «Открыть» и подтвердите запуск.

## Что делает аудит

Команда создаёт отдельный Markdown-отчёт для каждого запуска в соседней с `web-service` папке `../audits/code/`. Имя содержит дату и время, например `code-audit-2026-07-21-153000.md`.

Аудит проверяет:

- структуру проекта, примеры env и правила `.gitignore`;
- `git status` и опасные локальные файлы;
- npm build, tests, lint и typecheck/check, когда соответствующие scripts существуют;
- локальную сборку Docker image без запуска production-контейнера;
- localhost, если приложение уже запущено, и публичные production URL;
- свободное место production-сервера через SSH (`df -h`, `docker system df`, размер `/opt/zabota`);
- состояние контейнера `zabota-web`, размер Docker JSON-логов и последние 120 строк логов;
- наличие в production-логах `error`, `failed`, `not found`, Prisma и legal-ошибок;
- ключевое содержимое главной, `/app` и JSON-ответа `/api/health`, а не только HTTP status;
- API health и публичные/protected legal endpoints;
- фактическое наличие обязательных legal document keys в ответе `/api/legal/documents`;
- ссылки на `index.html` и старые маршруты;
- согласованность ключей юридических документов frontend и backend;
- contract формы и API регистрации, необязательный email, телефон, роль, город и согласия;
- список и поиск городов;
- запрещённую терминологию в UI и документации;
- demo-логины и тестовые данные;
- mock/T-Bank оплату, отсутствие полей банковской карты во frontend, баланс и trial-настройки;
- обязательные страницы и актуальный текст лендинга;
- ключи CORS/payment в `.env.production.example` и нежелательные кавычки.

Команда не исправляет код, не изменяет базу, не запускает контейнер и не выполняет deploy. Runtime-проверки используют безопасные HTTP-запросы без авторизации и read-only SSH-команды. Содержимое реальных `.env`, `.env.production` и `backend/.env` не читается и не попадает в отчёт.

SSH-проверка использует ключевое подключение к production с коротким таймаутом и без запроса пароля. По умолчанию проверяется настроенный production-хост; при необходимости его можно переопределить перед запуском через `PRODUCTION_SSH_HOST`. Сырые строки production-логов не записываются в локальный отчёт: сохраняются только количества совпадений, чтобы не раскрывать персональные данные, токены или другие чувствительные значения.

## Где лежат отчёты

Все отчёты сохраняются в:

```text
Проект забота рядом/audits/code/
```

Папка `audits` находится вне `web-service`, поэтому отчёты не смешиваются с рабочим кодом проекта. Старые отчёты можно удалять вручную, когда они больше не нужны.

## Если найдены критичные проблемы

Не запускайте следующий production deploy, пока не прочитаете разделы «Критичные проблемы» и «Технические детали». Исправляйте проблемы отдельно, затем повторно запустите аудит и выполните ручные проверки из отчёта. Сам аудит никаких исправлений не применяет.

Если Docker Desktop или localhost недоступны, соответствующая проверка будет отмечена как ошибка или пропущенная, но остальные этапы продолжатся.
