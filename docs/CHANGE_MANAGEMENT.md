# Управление изменениями

> Статус: ACTIVE PROCESS.

## Перед изменением

1. Прочитать [`AGENTS.md`](../AGENTS.md) и [`DOCUMENTATION_INDEX.md`](DOCUMENTATION_INDEX.md).
2. Определить затронутые домены и открыть source of truth и domain docs.
3. Проверить `git status --short`; не сбрасывать пользовательские изменения.
4. Найти фактические модели, endpoints, guards, serializers и tests.
5. Составить impact list и проверить legacy compatibility.
6. Не читать/менять production env и не полагаться на старый audit report как на текущее состояние.

## Во время изменения

- Сначала подтвердить бизнес-решение, затем менять код минимально.
- Сохранять обратную совместимость и исторические snapshots/ledger/legal acceptance.
- Добавлять backend/frontend tests пропорционально риску.
- Повышать snapshot schema version при несовместимом формате.
- Сохранять ownership guards, idempotency и AuditLog.
- Не редактировать active category structure или published legal version скрытно.
- Перед удалением структуры выполнять dependency check. Старые snapshots неизменяемы; актуализация заявки создаёт revision и новый snapshot только после подтверждения Заказчика.
- Опубликованная заявка с pending structure update скрыта от общей выдачи Помощникам на backend. Финализированные условия без финансовой delta не мигрируются.
- Экстренное отключение требует причины, AuditLog и определённого fallback.
- Не менять live T-Bank/production flags в обычной feature-задаче.

## После изменения

1. Обновить source of truth только при изменении продуктового решения.
2. Обновить доменный документ при изменении модели/API/поведения.
3. Обновить operational checklist при изменении операции.
4. Обновить README только при изменении запуска или верхнеуровневой архитектуры.
5. Обновить AGENTS при изменении обязательного процесса.
6. Добавить запись в [`DECISIONS_LOG.md`](DECISIONS_LOG.md), если изменилось бизнес-решение.
7. Выполнить tests/check/build/diff и безопасные domain checks.
8. В отчёте явно перечислить незавершённое и не считать draft готовой функцией.

## Минимальные проверки

```bash
npm run check
npm test
npm run build
git diff --check
```

Prisma generate выполняется при изменении schema. `db:push` направляется только на явно выбранную локальную/временную DB и никогда не использует `--accept-data-loss`. UI проверяется visual audit и, где требуется, реальным E2E, потому что mock routes не проверяют backend.

Изменение фоновой задачи должно иметь env switch, ручной single-run для тестов, управляемые часы, защиту от параллельного запуска и корректную остановку процесса. Однопроцессный lock нельзя описывать как распределённую гарантию.
# User Management & Security

Изменения ролей, административный сброс пароля и отзыв чужих сеансов выполняет только Суперадминистратор. Назначение/снятие manager требует комментария и отзывает старые JWT. Legacy `admin` нельзя автоматически преобразовывать: перед production-миграцией происхождение каждой такой записи проверяется вручную.
