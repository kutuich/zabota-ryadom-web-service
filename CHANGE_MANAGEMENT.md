# Управление изменениями

> Статус: ACTIVE PROCESS  
> Актуализировано: 2026-08-20

## 1. Перед изменением

1. Прочитать `AGENTS.md` и `docs/DOCUMENTATION_INDEX.md`.
2. Определить затронутые домены и открыть соответствующие active domain docs.
3. Если изменение затрагивает бизнес-логику/архитектуру — использовать актуальное утверждённое решение Notion, переданное в задаче или доступное исполнителю. Не восстанавливать его по старому Markdown.
4. Проверить `git status --short`; не сбрасывать пользовательские изменения.
5. Найти фактические models, endpoints, guards, serializers, services и tests.
6. Составить impact list и проверить legacy compatibility.
7. Не читать/менять production secrets и не считать старый audit report текущим состоянием.

Если необходимое архитектурное решение отсутствует или неоднозначно, не достраивать его самостоятельно. Зафиксировать вопрос и запросить утверждение.

## 2. Классификация изменения

### A. Только реализация
Не меняет утверждённое продуктовое поведение: bugfix, refactor, test, observability, безопасное улучшение реализации.

Действия: код → tests → domain/operational docs при необходимости.

### B. Реализация отстаёт от утверждённой архитектуры
Notion уже содержит целевое решение, код ещё старый.

Действия: зафиксировать gap → составить migration/compatibility plan → изменить код → tests → domain docs → проверить соответствие Notion.

### C. Новое продуктовое/архитектурное решение
Меняет правила продукта, данные, роли, деньги, legal, пользовательский путь или архитектурные границы.

Действия: сначала явное решение пользователя и актуализация Notion → затем реализация. Codex не создаёт новое бизнес-решение только из удобства текущего кода.

### D. Production/operational change
Меняет deploy, DB, provider, env, network, backup, scheduler или live integration.

Действия: отдельный impact/rollback plan, безопасная проверка и актуализация operational docs.

## 3. Во время изменения

- Менять код минимально относительно утверждённой цели.
- Сохранять обратную совместимость там, где она нужна для существующих данных/API.
- Сохранять immutable historical snapshots, ledger, legal acceptance и audit history.
- Добавлять backend/frontend tests пропорционально риску.
- Повышать snapshot/schema version при несовместимом формате.
- Сохранять ownership guards, idempotency и AuditLog.
- Не редактировать active service/category structure или published legal version скрытно.
- Перед удалением/архивированием структуры выполнять dependency check.
- Финализированные условия не мигрировать скрытно без утверждённой процедуры и, если требуется, финансовой delta.
- Не менять live T-Bank/production flags как побочный эффект feature-задачи.
- Не превращать ограничение текущей реализации (например SQLite/one-instance) в новое архитектурное правило.

## 4. После изменения

1. Проверить соответствие результата переданному утверждённому решению Notion.
2. Обновить domain doc при изменении фактической модели/API/поведения.
3. Обновить operational checklist при изменении операции.
4. Обновить README только при изменении запуска, стека или верхнеуровневой фактической реализации.
5. Обновить AGENTS только при изменении обязательного engineering process.
6. При значимом решении добавить краткую историческую запись в `docs/DECISIONS_LOG.md`; она не заменяет Notion.
7. Выполнить tests/check/build/diff и безопасные domain checks.
8. В отчёте перечислить незавершённое, manual-only и непроверенные части.
9. Если в ходе работы найдено новое расхождение code ↔ Notion, сообщить о нём отдельно; не исправлять архитектуру молча.

## 6. Минимальные проверки

```bash
npm run check
npm test
npm run build
git diff --check
```

Prisma generate выполняется при изменении schema. Миграционные/DB-команды направляются только на явно выбранную среду. Destructive operation без backup/rollback и явного основания запрещена.

UI проверяется visual audit и, где риск требует, реальным E2E; mock routes не доказывают корректность backend integration.

## 7. Фоновые задачи и масштабирование

Изменение scheduler/background job должно иметь управляемый запуск/выключение, single-run способ проверки, защиту от параллельного выполнения, корректную остановку, идемпотентность и понятный recovery/catch-up.

Однопроцессный mutex нельзя описывать как distributed guarantee. Текущая одноинстансовая реализация не отменяет целевую архитектуру масштабирования в Notion.

## 8. Security-sensitive изменения

Изменения ролей, административного сброса пароля, JWT/session invalidation, payments, legal acceptance, адресных/контактных DTO и production integrations требуют отдельной проверки guards, AuditLog, тестов и обратной совместимости.
