# AGENTS.md — обязательные правила работы с репозиторием

> Статус: ACTIVE PROCESS
> Актуализировано: 2026-08-20

## 1. Роль этого файла

Этот файл определяет **как Codex/разработчик должен работать с репозиторием**. Он не является источником продуктовой архитектуры и не заменяет Notion.

## 2. Источники истины и разрешение конфликтов

Приоритет:
1. Явное решение пользователя в текущей задаче.
2. Актуальная утверждённая архитектура и проектные данные в Notion.
3. Утверждённые юридические документы и требования к конкретному изменению.
4. GitHub/локальная рабочая копия — источник истины о **фактически реализованном коде**, schema, API, тестах, deployment и текущем production-состоянии.
5. Активные доменные и operational документы репозитория — описание реализации и процедур.
6. Исторические Markdown, старые экспорты TheBrain, audit snapshots и переписка.

Код не отменяет архитектуру. Если код расходится с утверждённой архитектурой Notion, это считается расхождением реализации до отдельного архитектурного решения.

Codex не должен восстанавливать продуктовую архитектуру по старым Markdown или по коду.

Если задача меняет бизнес-логику, а актуальное решение Notion не передано в задаче и недоступно Codex, нужно остановиться на границе неопределённости и запросить соответствующий утверждённый фрагмент/решение. Не придумывать новое продуктовое правило.

## 3. Перед работой

1. Открыть `docs/DOCUMENTATION_INDEX.md`.
2. Прочитать технический документ затрагиваемого домена.
3. Проверить `git status --short`. Локальная рабочая копия может быть новее GitHub; пользовательские изменения не сбрасывать.
4. Найти фактические модели, endpoints, guards, serializers, services и tests затрагиваемого домена.
5. Сопоставить задачу с переданным утверждённым решением/требованием Notion, если задача затрагивает продуктовую архитектуру.
6. Определить impact: данные, API, UI, финансы, legal, security, production, миграции, обратная совместимость.
7. Не выдавать technical draft или частичную реализацию за готовое продуктовое решение.

## 4. Защитные инварианты текущей реализации

Ниже перечислены действующие защитные ограничения. Это не самостоятельный Source of Truth; при утверждённом изменении архитектуры они должны быть пересмотрены вместе с кодом и документацией.

- Новая заявка использует версионную service structure и выбранные задачи/узлы; legacy-модель не возвращать как основной путь.
- График конечный. Один конкретный непересекающийся слот на дату соответствует одному визиту.
- Стоимость рассчитывается отдельно по визитам; итог графика — сумма рассчитанных визитов.
- Текущая модель сервисного сбора: 50 ₽ с Заказчика и 50 ₽ с Помощника за каждый согласованный визит.
- Создание заявки, отклик и чат сами по себе не списывают сервисный сбор.
- Финализация финансовых обязательств выполняется только после подтверждения обеими сторонами одной актуальной версии условий.
- Оплата помощи проходит напрямую между Заказчиком и Помощником; внутренний баланс сервиса используется для сервисного сбора.
- Внутренний резерв — аналитический показатель, не депозит, эскроу и не банковская блокировка.
- Published legal versions, active category/service structures, live T-Bank и production env не меняются скрытно или в обычной feature-задаче без отдельного основания.
- Исторические snapshots, ledger, legal acceptance и audit history не переписываются задним числом.

## 5. Терминология UI

Использовать публично: **Заказчик, Помощник, Подопечный, сервисный сбор, бытовая помощь, сопровождение, уход на дому без медицинских процедур, согласованный визит**.

Не использовать публично без отдельного утверждённого изменения: **клиент, исполнитель, комиссия, работник, сотрудник, нанять, трудоустройство, медицинские услуги**.

Технические legacy-имена (`client`, `performer`, `ClientRequest` и т. п.) допустимы внутри кода до отдельной безопасной миграции.

## 6. Legal, персональные данные и адреса

- Публичные legal-маршруты должны оставаться доступными в соответствии с текущим контрактом реализации.
- Опубликованная версия юридического документа не редактируется напрямую; новая редакция получает новую версию/hash.
- Закрытые персональные и адресные поля не должны попадать в публичные DTO, логи, ссылки или сообщения.
- Политика раскрытия адреса и контактов должна проверяться по актуальному утверждённому требованию Notion и соответствующему domain doc перед изменением.
- Secrets, пароли, hashes, OAuth/T-Bank credentials и raw tokens не выводить в документацию, AuditLog или пользовательские сообщения.

## 7. Изменения

Следовать `docs/CHANGE_MANAGEMENT.md`.

При изменении реализации:
- обновить соответствующий domain doc и тесты;
- создать новую schema/snapshot version при несовместимом формате;
- сохранить ownership guards, idempotency, AuditLog и историческую воспроизводимость;
- не использовать существующий код как основание для молчаливого изменения продуктового решения.

При изменении продуктового решения:
- решение сначала должно быть явно утверждено пользователем и отражено в Notion;
- затем меняются код, domain docs и тесты;
- в `docs/DECISIONS_LOG.md` добавляется краткая историческая запись, если это полезно для понимания эволюции реализации;
- `DECISIONS_LOG.md` не заменяет Notion.

## 8. Production

- Не читать и не менять production secrets без отдельной необходимости и явного разрешения.
- Не менять live T-Bank, production flags, published legal documents или active structures как побочный эффект другой задачи.
- Миграции БД должны иметь безопасный план, backup/rollback и проверку данных.
- Текущая SQLite/однопроцессная конфигурация является фактом текущей реализации, а не целевой архитектурной нормой. Целевое состояние определяется Notion.

## 9. Минимальные проверки

```bash
npm run check
npm test
npm run build
git diff --check
```

При изменении Prisma schema выполнить generate и необходимые безопасные проверки миграции. Не направлять destructive DB-команды на production. Для UI запускать доступный visual/E2E audit, соответствующий риску изменения.

## 10. Отчёт после работы

В отчёте указать:
- изменённые файлы;
- миграции/schema changes;
- изменённые API/UI/модели;
- обновлённую документацию;
- выполненные команды и результаты;
- влияние на данные, финансы, legal, security и production;
- обратную совместимость;
- всё, что осталось незавершённым;
- обнаруженные расхождения с утверждённой архитектурой Notion.

Не объявлять задачу полностью завершённой, если обязательная часть осталась draft, manual-only или не проверена.
